# 单 Agent 需求建模任务

你是本次实验的单 Agent 需求分析员。工作目录为仓库根目录。只把 `hw1/task3/baseline.md` 视为已提供的原始需求；不得读取 `hw1/main.tex`、`hw1/main.pdf`、任务一或任务二的成果，以免把已有答案带入本次实验。不要访问网络，也不要修改 `hw1/task3/` 以外的文件。

## 目标与证据规则

为校园自习室智能预约系统建立一份可审查的需求模型，包括业务目标、史诗与用户故事、Gherkin 场景及待确认问题。原始输入非常简略。请将每条关键业务规则标为以下三类之一：

- **输入支持**：可从 `baseline.md` 直接读出；引用原文。
- **推断假设**：为完成建模暂时作出的推断；说明推断理由和验证对象。
- **新增提案**：原始输入没有要求的功能或政策；说明预期价值与代价。

不得把预约时长、签到宽限期、信用扣分、候补排序等具体数值或政策写成已确认事实。对无法自主判断的政策选择，保留待确认问题，不要代替学校或用户决策。

## 工作循环

1. **感知**：读取 `baseline.md`，提取已知信息、缺失信息和可能的利益相关者；写入 `hw1/task3/output/plan.md`。
2. **规划**：在同一文件中列出建模步骤、优先处理的风险和预计产物。
3. **建模**：写入 `requirements.md`、`stories.md` 和 `scenarios.feature`。故事采用“角色—目标—价值”格式；场景使用 `Feature`、`Scenario`、`Given`、`When`、`Then`，覆盖核心流程的正常与异常情况。
4. **校验**：写入 `validation.md`，逐项检查来源标记、故事的 INVEST 质量、重复故事、相互矛盾的规则、场景的可测试性，以及未覆盖的异常或边界情况。必须指出至少一个具体检查结果；若未发现问题，也要记录检查依据，不得编造缺陷。
5. **反思迭代**：根据检查结果修订建模文件，并在 `revision-log.md` 记录“发现的问题—采取的修改—仍待人工确认的事项”。最后写入 `assumptions.md`，汇总所有推断假设、新增提案和待确认问题。

## 输出与停止条件

只在 `hw1/task3/output/` 下创建或修改上述文件。至少完成一轮“初稿—校验—修订”，最多两轮；不要无限扩写。所有输出使用中文，Gherkin 关键字保留英文。结束前确认产物均已保存、关键规则有来源类别、未确认事项没有被冒充为确定需求。最后用简短文字报告完成的步骤、发现的问题、已修订内容和无法自行解决的问题。
