# 感知与规划（plan.md）

## 一、原始需求回顾

`baseline.md` 全文仅一句话：

> 「现在需要开发一个『校园自习室智能预约系统』。」

这是本次建模唯一被提供的原始输入。除此之外不得引用任何既有答案文件。

## 二、感知：已知信息（输入支持）

从原文可直接读出的信息只有：

| 编号 | 已知信息 | 原文依据 |
| --- | --- | --- |
| K1 | 系统面向「校园」场景 | 「校园自习室智能预约系统」 |
| K2 | 业务对象是「自习室」 | 「校园自习室智能预约系统」 |
| K3 | 核心功能是「预约」 | 「智能预约系统」 |
| K4 | 系统被定位为「智能」的 | 「智能预约系统」 |
| K5 | 需要「开发」一个系统，即产出可用的软件 | 「现在需要开发一个……」 |

以上 5 条构成需求模型的全部确定边界，其余内容都需要标为**推断假设**或**新增提案**。

## 三、感知：缺失信息（需要建模补齐或列为待确认）

原文未提供以下任何一项：

1. 用户角色（学生、教师、管理员？是否需要校外/访客？）
2. 预约对象粒度（整间自习室 / 单个座位 / 时间段？）
3. 预约时长、可预约时间窗口、提前预约天数等具体数值
4. 签到与签退方式（扫码、刷卡、定位？）及签到宽限期
5. 违规与信用机制（是否扣分、扣多少、如何恢复）
6. 候补（waitlist）规则与排序策略
7. 取消、修改、爽约的处理政策
8. 「智能」具体指什么（推荐、预测、自动分配、冲突消解？）
9. 与学校既有系统（统一身份认证、校园卡、课表）的集成方式
10. 非功能需求（并发量、可用性、隐私与数据合规）
11. 管理端能力（增删自习室、封禁、统计报表）
12. 成功指标与验收标准

## 四、可能的利益相关者（推断假设，待确认）

- 学生（主要预约者）
- 教师 / 教职工（可能的预约者）
- 自习室/图书馆管理员（资源维护者）
- 学校信息化部门（系统所有者、运维方）
- 校方管理层（政策制定者，决定时长、信用等规则）
- 安保/物业（现场秩序）

## 五、建模步骤（规划）

1. 依据 K1–K5 确定系统范围与边界，写出业务目标。
2. 将原文未给出但建模必需的内容显式拆分为「推断假设」与「新增提案」。
3. 产出业务目标、史诗（Epic）与用户故事（角色—目标—价值）。
4. 为用户故事编写 Gherkin 场景，覆盖正常流程与异常/边界流程。
5. 每条关键业务规则标注来源类别：输入支持 / 推断假设 / 新增提案。
6. 编写校验文档，逐项检查来源标记、INVEST 质量、重复、矛盾、可测试性与异常覆盖。
7. 根据校验结果修订，并记录修订日志与假设汇总。

## 六、优先处理的风险（推断假设层面的风险最高）

| 优先级 | 风险 | 处理方式 |
| --- | --- | --- |
| 高 | 具体数值政策（时长、宽限期、扣分、候补排序）被误当成确定需求 | 一律标为推断假设 + 待确认问题，不写死数值 |
| 高 | 「智能」含义不明确，可能被过度设计 | 仅提出最小可解释的智能能力，并列为待确认 |
| 高 | 角色与权限边界不明，导致越权操作 | 明确默认角色模型，并列为待确认 |
| 中 | 资源粒度（整间 vs 座位）影响数据模型 | 作为关键待确认问题前置 |
| 中 | 与既有校园系统集成范围不明 | 列为待确认，不假设已有接口 |
| 低 | 非功能需求缺失 | 先给可验证的占位指标方向，具体阈值待确认 |

## 七、预计产物

- `plan.md`：本文件，感知与规划。
- `requirements.md`：业务目标、范围、关键业务规则（含来源标记）。
- `stories.md`：史诗与用户故事。
- `scenarios.feature`：Gherkin 正常与异常场景。
- `validation.md`：校验结果。
- `revision-log.md`：发现的问题—采取的修改—待确认事项。
- `assumptions.md`：推断假设、新增提案、待确认问题汇总。

## 八、停止条件

至少完成一轮「初稿—校验—修订」，最多两轮，不无限扩写。所有输出为中文，Gherkin 关键字保留英文。
