# 假设与待确认事项汇总（assumptions.md）

本文件汇总全部 **推断假设**、**新增提案** 与 **待确认问题**，是需求模型「哪些是猜的、哪些要人来决定」的最终清单。

## 一、推断假设（为建模暂时作出，需验证）

| 编号 | 假设内容 | 推断理由 | 验证对象 |
| --- | --- | --- | --- |
| A1 | 用户需通过校园身份认证 | 面向校园的文字暗示需绑定真实身份 | 学校信息化部门 |
| A2 | 预约是对某资源在指定时段的独占 | 「预约」语义的必要组成 | 自习室管理员 |
| A3 | 预约对象可为自习室/座位等资源 | 原文只说「自习室」，粒度需细化 | 产品负责人（见 Q2） |
| A4 | 提供取消能力 | 无取消则预约不可用 | 业务方 |
| A5 | 提供签到与签退机制以防占座 | 校园自习室常见治理手段 | 管理员 |
| A6 | 存在违约与信用记录的概念（仅概念，不含数值） | 签到/爽约治理的常见延伸 | 校方政策制定者（见 Q7） |
| A7 | 满员可有候补队列 | 提升公平性与利用率 | 业务方（见 Q8） |
| A8 | 「智能」= 推荐可用资源/消解冲突 | 对原文「智能」的最小可验证解释 | 产品负责人（见 Q9） |
| A9 | 用户只能操作自己的预约，管理员按权限查看全部 | 最小权限原则 | 信息安全/合规方 |
| A10 | 高并发、并发一致性、移动端体验是重点 | 校园高峰与手机用户推断 | 运维与用户代表（见 Q11） |
| A11 | 业务目标为减少占座、提升利用率 | 预约系统的通用目标 | 校方（见 G1、G2） |

## 三、待确认问题（须由学校/用户决策，不得替代决定）

| 编号 | 问题 | 为什么必须由人确认 | 关联 |
| --- | --- | --- | --- |
| Q1 | 用户角色有哪些（学生/教师/管理员/访客）？ | 决定权限模型 | A1、A9、US-7.1 |
| Q2 | 预约粒度：整间自习室还是单个座位？ | 决定数据模型与并发粒度 | A3、US-2.1 |

| Q4 | 可取消的时限规则？ | 政策选择 | BR-4、US-3.3 |
| Q5 | 签到方式（扫码/刷卡/定位）？ | 依赖现场设施与集成 | BR-5、US-4.1 |
| Q6 | 签到宽限期具体时长？ | 政策选择，不能写死 | BR-5、US-4.1 |

| Q12 | 是否禁止同一用户在同一时段预约不同资源？ | 政策选择；已按校验 P3 不写死 | BR-3、US-3.2 |

## 四、明确未写成确定事实的内容（对照检查）

以下内容在需求模型中**没有任何一处**被写成已确认的具体数值或政策：

- 预约时长、可预约时间窗口、提前预约天数 → 见 Q3。
- 签到宽限期 → 见 Q6。
- 信用扣分数值与恢复规则 → 见 Q7。
- 候补排序规则与通知有效期 → 见 Q8。
- 跨资源同时段预约是否禁止 → 见 Q12。

以上均以「待确认问题 + 占位说明」的形式保留，未冒充为确定需求。
